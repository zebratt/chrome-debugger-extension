# 第1轮评审意见
评审时间：2026-09-29
评审方案版本：plan_v1
评审模式：full
启用轴：C1,C2,C3,C4,X2,X3

## C1 目标、范围与非目标
### 结论
通过 — 目标、范围、非目标基本清楚，且与 `meta.md` 中已确认前提一致。

### 发现
无阻塞发现

## C2 架构与模块边界
### 结论
有条件通过 — 模块切分方向合理，但按需 broker 的启动与恢复时序还不够收束，执行者仍需补猜。

### 发现
- [P1] `§3`、`§4.2`、`§4.3` 没有把“小宿主已连扩展但 broker 未启动 / broker 刚启动等待 profile 注册 / broker 重启后宿主重连”三类状态收成明确状态机。按“首个 agent 拉起 broker 后立刻调用 `browser.list` 或 `tab.list`”推演，当前方案没有说明客户端应看到“初始化中、离线、空列表”中的哪一种，也没有注册等待时限。建议在架构节补一张生命周期时序或状态表，明确各状态、超时和对外可见语义。

## C3 接口/数据/兼容合同
### 结论
不通过 — 公共接口方向对了，但核心合同还不足以支撑 CLI、MCP、skill 三个入口独立实现而不分叉。

### 发现
- [P1] `§5` 只列了方法组和方法名，没有补足多配置文件场景下的最小请求/响应合同。当前不清楚 `profileId` 在哪些方法中必填、0/1/N 个 profile 在线时默认选择规则是什么、`tabId` 是否仅在 profile 内唯一。建议至少为 `browser.list`、`tab.list`、`tab.open`、`tab.navigate` 补最小字段表和默认行为。
- [P1] `§4.3`、`§5` 未定义 `tab.claim/tab.release` 的 TTL、续租、重入、broker 重启/客户端断连后的失效语义，也未说明哪些写方法强制附带 `leaseToken`。按“agent A `tab.claim` 后退出，agent B 再 `tab.click`”推演，现有方案无法唯一推出锁释放与冲突判定。建议把占用权合同单列成一小节。
- [P1] `§5` 对 `snapshotId`、节点引用、截图交付和 `cdp.send` 能力发现都只写了原则，没有最小结构。执行者仍需猜“节点引用长什么样、截图是内联字节还是句柄、客户端如何先知道允许的 CDP 域”。建议补 `tab.snapshot` 结果形态、`tab.screenshot` 返回模式，以及 `system.capabilities` 或等价能力发现接口。

## C4 风险、回滚与遗漏
### 结论
有条件通过 — 已识别主要风险，但“结果未知”场景的恢复路径还没有闭环。

### 发现
- [P1] `§4.3`、`§6`、`§7` 只说明“非幂等页面操作不自动重试”“断线期间不假定成功或失败”，但没有定义客户端在宿主断线、broker 退出、`TARGET_DETACHED` 后如何恢复。按“`tab.click` 已发出后宿主断线”推演，调用方缺少统一的后续动作。建议补一个明确的“结果未知”语义：专用错误码或状态、必须重新快照还是人工确认、以及相关 `leaseToken` 如何清理。

## X2 安全与隐私
### 结论
有条件通过 — 信任边界写清了，但安全默认值还没有落成可执行合同。

### 发现
- [P1] `§5`、`§6` 只说 `cdp.send` “可配置开启”、网站规则“再次校验”，没有定义默认值、配置归属、是否允许请求侧覆盖、以及客户端如何读取当前策略。考虑到本方案已接受“同 UID 无逐客户端授权”，这里就是首版最关键的安全收口。建议明确：策略文件由 broker 独占管理、`cdp.send` 默认关闭、允许域为显式 allowlist、调用方只能查询不能覆盖。
- [P2] `§4.2`、`§5`、`§7` 提到截图临时文件和诊断日志，但没有补充 retention、清理触发点和错误上下文脱敏规则。建议在非功能或安装回滚节补充最小保留策略。

## X3 迁移与兼容
### 结论
不通过 — 兼容原则有了，但升级与回滚锚点还没有锁住。

### 发现
- [P0] `§4.2`、`§6`、`§7` 一方面要求“固定扩展 ID”“Native Messaging 清单使用精确 `allowed_origins`”，另一方面又把“实际安装路径和分发方式”留到实施前再定。这会直接影响扩展 ID 稳定性、宿主清单生成方式、升级替换路径和失败回滚点。按“先做 v1，再调整分发形式或安装路径”推演，现有方案无法保证既有安装不失效。建议在实施前先锁定交付模型和版本化安装布局；若还需验证，就把这一步提升为前置 spike，再回写方案。
- [P1] `§5`、`§6` 只写了“协议版本协商、版本不兼容时明确报错”，没有给 CLI/MCP、broker、小宿主、扩展之间的支持矩阵、先后升级顺序和双轨期。建议补一张兼容矩阵，至少说明同主版本支持范围、谁必须先升级、`doctor` 在发现旧组件时给什么 remediation。

## 总体评价
需要修改

## 修改建议优先级
### P0 必须修改
- 锁定固定扩展 ID、宿主清单和安装路径的交付模型，不要带着该未决进入实现。对应 `§4.2`、`§6`、`§7`。

### P1 建议修改
- 补齐 broker 启动、宿主登记、客户端首个请求的状态机与超时语义。对应 `§3`、`§4.2`、`§4.3`。
- 补齐公共接口最小合同，尤其是 `profileId/tabId` 选择规则、`tab.claim` 语义、`snapshotId`/节点引用、截图交付和能力发现。对应 `§5`。
- 补齐“结果未知”场景的恢复路径，避免非幂等操作在断线后无统一处置。对应 `§4.3`、`§6`、`§7`。
- 明确 broker 独占的安全策略合同，包括 `cdp.send` 默认关闭、域 allowlist 和站点规则的读取方式。对应 `§5`、`§6`。
- 增加组件版本错配的兼容矩阵和升级顺序。对应 `§5`、`§6`。

### P2 可选优化
- 补充截图临时文件、诊断日志和错误上下文的最小脱敏与保留策略。对应 `§4.2`、`§5`、`§7`。
